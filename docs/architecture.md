# 学院学生综合服务与党团管理平台架构约束

## 1. 建设目标

本文档根据甲方《产品需求文档：学院学生综合服务与党团管理平台》整理，用于约束后端建模、前端页面拆分和接口联调。一期系统面向学院内部约 1200 名本科生、研究生、班团骨干、管理老师和学院领导，采用前后端分离 Web 方案，兼顾移动端高频办理和 PC 端批量管理。

一期主线：

- 智能问答与政策知识库，P0
- 党团事务流程管理，P0
- 学生画像与信息管理，P1
- 奖励荣誉展示，P1
- 信息集成与精准推送，P1
- 电子证明生成与院内审批，P1

后续扩展：

- 学业情况分析与预警，P2，只保留数据库和接口扩展位，不作为一期核心验收流程。

## 2. 技术边界

- 前端：学生端优先适配手机浏览器，管理端优先适配 PC 浏览器；同一接口返回结构不因端而异。
- 后端：提供 RESTful JSON API，基础路径统一为 `/api/v1`。
- 数据库：人大金仓 Kingbase，SQL 以 PostgreSQL 兼容语法为基线。
- 文件：一期必须支持 PDF、Word、Excel 上传、下载和导出；政策文件单文件建议上限 30MB。
- 通知渠道：站内消息、邮件、微信提醒需要留接口和发送记录；短信只保留模拟发送记录。
- 外部系统：一期不直接对接校级系统，学生、成绩、政策等数据通过导入、上传或后台维护进入平台。

## 3. 角色与权限

系统固定四类核心角色，后端必须同时做接口权限和数据范围校验，前端只做展示控制。

| 角色 | 代码建议 | 数据范围 | 主要能力 |
| --- | --- | --- | --- |
| 普通学生 | `student` | `self` | 查看个人档案、通知、党团进度，提交材料和申请 |
| 班团骨干 | `class_cadre` | 授权班级或支部 | 查看授权范围内成员进展，辅助催办和信息收集 |
| 管理老师 | `teacher_admin` | 授权年级、专业、班级或学院 | 维护知识库、学生信息、通知、流程、审批、导入导出 |
| 学院领导 | `college_leader` | 学院汇总 | 查看统计看板、重点问题和运行情况，不默认开放日常审批 |

数据范围代码：

- `self`：本人
- `class`：班级
- `branch`：党支部或团支部
- `major`：专业
- `grade`：年级
- `department`：学院
- `global`：全局，原则上只给系统管理员

权限实现约束：

- `sys_role.data_scope` 是默认范围，`sys_user_scope` 存用户实际可访问的班级、年级、支部等明细。
- 学生敏感字段默认不返回原文；老师查询敏感字段时必须写入 `audit_log`。
- 助教或临时协助人员不得拥有正式审批权限，只能配置只读或协办权限。

## 4. 业务域划分

### 4.1 用户与权限域

核心表：

- `sys_user`：登录账户，学生账户通过 `student_id` 绑定学生档案。
- `sys_role`、`sys_permission`：角色和权限点。
- `sys_user_role`、`sys_role_permission`：授权关系。
- `sys_user_scope`：用户可访问的数据范围。

前端约束：

- 登录后必须调用 `/auth/me` 获取角色、菜单和数据范围。
- 不同角色可共用页面组件，但按钮级能力必须由接口返回的权限码控制。

### 4.2 学生画像与信息域

核心表：

- `stu_student`：学号、姓名、年级、专业、班级、政治面貌等基础信息。
- `stu_student_ext`：生源地、户籍地、导师、经济困难等级、就业意向、修学/延毕记录等敏感扩展信息。
- `stu_tag`、`stu_student_tag`：标签定义和学生标签。
- `stu_growth_record`：科研竞赛、社会实践、志愿服务、干部任职、奖惩经历。
- `stu_import_task`：Excel 批量导入任务与错误报告。

数据展示约束：

- 普通学生只能查询本人完整档案。
- 班团骨干只能查询授权范围内的非敏感摘要字段。
- 管理老师可按权限查询敏感字段，接口必须记录审计日志。
- 批量导入必须先返回任务号，导入结果异步查询，不能让前端长时间等待。

### 4.3 智能问答与政策知识库域

核心表：

- `kb_category`：分类，如奖助、学籍、党团、证明、就业、宿舍。
- `kb_article`：知识条目，必须包含摘要、标准答案或正文。
- `kb_article_version`：历史版本，过期政策不可直接覆盖丢失。
- `kb_template`：常用 Word、Excel 模板下载。
- `kb_question_log`：学生提问、回答、来源和反馈。
- `file_resource`：政策附件和模板文件。

问答约束：

- 回答必须优先基于 `standard_answer`、`summary`、`content` 和原始附件，不允许无来源自由生成。
- 问答结果必须返回 `sources`，包含知识条目 ID、标题、附件名或原文链接。
- 知识条目支持 `draft`、`published`、`disabled`、`expired` 状态。
- 管理端更新已发布知识时必须生成 `kb_article_version`。

### 4.4 党团事务流程域

核心表：

- `flow_definition`：流程定义，如入党流程、入团流程。
- `flow_stage_definition`：阶段定义，如入党申请人、积极分子、发展对象、预备党员、正式党员。
- `flow_instance`：某学生的一条流程实例。
- `flow_stage_record`：阶段进度、截止时间、审核意见。
- `flow_material`：阶段材料提交与审核。
- `flow_action_log`：提交、通过、退回、撤回、重批等全量留痕。
- `flow_exam_question`：党建/团建理论自测题库，可选。

流程约束：

- 党团流程是固定线性流程，前端按 `stageOrder` 渲染完整时间线。
- 学生只能提交本人当前阶段材料。
- 老师审核可通过、退回、补充说明。
- 审批结果允许在限定时间内撤回或重批，建议 1 至 2 天；撤回和重批必须新增日志，不允许覆盖旧记录。
- 班团骨干只能查看授权范围内进展和催办信息，不能执行正式审批。

### 4.5 通知与精准推送域

核心表：

- `msg_notice`：通知正文、标签、有效期和发布状态。
- `msg_notice_scope`：目标对象规则，如年级、专业、班级、标签、政治面貌。
- `msg_notice_user`：站内消息触达和已读状态。
- `msg_delivery_record`：邮件、微信、短信模拟等渠道发送结果。
- `msg_notice_attachment`：通知附件。

推送约束：

- 发布通知时，后端根据范围规则计算接收人并落库到 `msg_notice_user`，前端不负责目标匹配。
- 已读、未读、发送失败必须可统计。
- 通知支持草稿、定时发布、归档和过期。
- 微信和邮件失败不影响站内消息生成，但必须记录失败原因。

### 4.6 荣誉展示域

核心表：

- `honor_record`：个人或集体荣誉，包含年份、类别、公开状态、展示顺序、展示时效、先进事迹和图片。

展示约束：

- 学生端或公开展示页只展示 `public_status=published` 且在展示时间范围内的数据。
- 管理端可以维护隐藏、发布、下线和排序。

### 4.7 证明与院内审批域

核心表：

- `cert_template`：证明模板、表单配置和审批规则。
- `biz_application`：请假、盖章、证明等院内申请主表。
- `biz_approval_record`：审批动作记录。

审批约束：

- 证明生成必须从学生基础信息和模板配置填充，生成文件写入 `generated_file_id`。
- 申请状态变化只能通过审批接口完成，不能由前端直接提交任意状态。
- 申请人可查看当前节点、处理人、审批意见和生成文件。
- `application_type` 至少支持 `certificate`、`leave`、`seal`，一期可优先实现 `certificate`。

### 4.8 学业预警扩展域

核心表：

- `academic_program`：培养方案要求。
- `academic_warning`：学业预警结果。

一期约束：

- 不做成绩单自动解析主流程。
- 只允许作为后续扩展位或手工录入演示数据。

### 4.9 审计与文件域

核心表：

- `audit_log`：管理员操作、敏感字段访问、审批动作和导入导出记录。
- `file_resource`：所有上传文件的统一索引。

审计约束：

- 管理端新增、修改、删除、导入、导出、审批、查看敏感字段都要写审计。
- 审计至少包含操作人、时间、对象、行为类型、接口路径、结果。
- 文件不直接存数据库，数据库只保存 URL、大小、哈希、业务归属。

## 5. 状态枚举

学生状态：

- `active`：在读
- `graduated`：毕业
- `suspended`：休学
- `withdrawn`：退学
- `transferred`：转专业
- `delayed`：延毕

知识库状态：

- `draft`：草稿
- `published`：已发布
- `disabled`：已停用
- `expired`：已过期

通知状态：

- `draft`：草稿
- `scheduled`：定时发布
- `published`：已发布
- `archived`：已归档
- `expired`：已过期

流程实例状态：

- `processing`：办理中
- `completed`：已完成
- `suspended`：暂停
- `cancelled`：已取消

流程阶段和材料状态：

- `pending`：未开始
- `submitted`：已提交
- `reviewing`：审核中
- `approved`：已通过
- `returned`：已退回
- `revoked`：已撤回

院内申请状态：

- `draft`：草稿
- `submitted`：已提交
- `reviewing`：审核中
- `approved`：已通过
- `rejected`：已驳回
- `revoked`：已撤回
- `archived`：已归档

发送状态：

- `pending`：待发送
- `success`：发送成功
- `failed`：发送失败
- `mocked`：模拟发送

## 6. 接口通用约定

- 基础路径：`/api/v1`
- 鉴权：`Authorization: Bearer <token>`
- 时间格式：`yyyy-MM-dd HH:mm:ss`
- 日期格式：`yyyy-MM-dd`
- 主键类型：JSON 中返回 number，前端如遇精度问题可按 string 处理。
- 分页参数：`pageNo` 从 1 开始，`pageSize` 默认 10，最大 100。
- 删除策略：核心业务表逻辑删除，字段为 `isDeleted`。
- 文件上传：统一使用 `/files/upload`，业务接口只传 `fileId`。
- 错误响应：HTTP 状态码与业务 `code` 同时返回，前端以业务 `code` 展示明确错误。

统一响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "requestId": "202605111230001234"
}
```

## 7. 前后端协作约束

- 前端不得写死枚举中文名，应使用接口返回的 `label` 或本地统一字典。
- 前端列表页必须保留分页、筛选、空状态、加载状态和错误状态。
- 后端必须对所有 ID 做归属校验，例如学生不能通过改 URL 查看他人申请。
- 后端必须在接口层统一做数据脱敏，不能依赖前端隐藏字段。
- 管理端导出接口需要按当前用户数据范围过滤。
- 站内通知、审批待办和党团待办应提供 dashboard 聚合接口，避免前端拼多个接口造成首屏过慢。

## 8. 一期不做或弱化

- 不直接对接校级“微人大”等外部系统。
- 不实现正式短信发送，只记录模拟发送。
- 不实现通用 BPM 引擎，党团流程和院内申请按当前需求轻量建模。
- 不实现成绩单自动解析和培养方案自动比对主流程。
- 不开放学生自助修改全部档案字段，敏感字段必须由管理员维护或审核。
